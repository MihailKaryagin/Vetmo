# Запуск vetmo

Локальный запуск использует существующую MySQL-базу и режим разработки:

```powershell
.\venv\Scripts\python.exe manage.py check_database
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py runserver
```

## Production

Задайте переменные окружения на сервере (PowerShell-пример):

```powershell
$env:DJANGO_DEBUG = 'false'
$env:DJANGO_SECRET_KEY = '<случайный секрет длиной не менее 50 символов>'
$env:DJANGO_ALLOWED_HOSTS = 'example.com,www.example.com'
$env:DJANGO_CSRF_TRUSTED_ORIGINS = 'https://example.com,https://www.example.com'
$env:MYSQL_DATABASE = 'djan'
$env:MYSQL_USER = 'vetmo'
$env:MYSQL_PASSWORD = '<пароль отдельного пользователя базы>'
$env:MYSQL_HOST = 'localhost'
$env:MYSQL_PORT = '3306'
.\venv\Scripts\python.exe manage.py check --deploy
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py collectstatic --noinput
```

Production-режим требует секрет и пароль БД, включает HTTPS-редирект, secure cookies и HSTS. Настройте HTTPS в reverse proxy и WSGI/ASGI-сервер для Django. `DJANGO_TRUST_PROXY=true` включайте только если собственный proxy очищает и сам выставляет `X-Forwarded-Proto`.

Пароль существующего MySQL-пользователя не меняется автоматически: создайте отдельного пользователя приложения с доступом к его базе и укажите его реквизиты через переменные выше. Настройки читаются также из `.env` в корне проекта. Переменные окружения имеют приоритет. `.env` исключён из Git.

## Новые разделы

- `/players` — игроки и фильтры; профили заполняются в админке → «Люди».
- `/events` — будущие события, регистрация и календарь; отображаются московское время и время часового пояса профиля.
- `/party` — объявления и отклики. Управление своим объявлением привязано к текущему браузеру; отклики видны автору и администратору.
- `/store` — каталог; заказы доступны в админке → «Заказы мерча». Оплата и доставка согласуются оператором, онлайн-эквайринг не подключён.

Объявления пати автоматически скрываются по истечении указанного срока. Заказ сохраняет цену товара и резервирует общее количество товара. Если в админке заданы размеры с остатками, одновременно резервируется выбранный размер. Общий остаток и остатки размеров должны соответствовать реальному складу. У старых товаров без вариантов сохраняется прежний учёт.

## Установка с нуля

Требуется Python 3.13 и MySQL 8.4. База должна использовать utf8mb4.

```powershell
python -m venv venv
.\venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
```

Заполните `.env` реквизитами отдельного MySQL пользователя. Пример SQL из учётной записи администратора MySQL:

```sql
CREATE DATABASE djan CHARACTER SET utf8mb4;
CREATE USER 'vetmo'@'localhost' IDENTIFIED BY 'replace_with_a_strong_password';
GRANT ALL PRIVILEGES ON djan.* TO 'vetmo'@'localhost';
```

Для тестов пользователь должен иметь права на создание и изменение `test_djan`. На production эти права приложению не нужны.

Запускайте `start_support.bat` из корня проекта. Он проверяет зависимости и соединение с базой, применяет миграции и запускает сайт. Если MySQL остановлен, запустите `Start-Service MYSQL84` из PowerShell администратора. Имя службы зависит от установки MySQL.

После миграций создайте администратора:

```powershell
.\venv\Scripts\python.exe manage.py createsuperuser
```

## Кабинет и магазин

- `/` — главная с новостями, ближайшим событием и активными пати.
- `/account/signup/` — регистрация, `/account/` — профиль, заявки, события, объявления, заказы и уведомления.
- Объявления авторизованного пользователя доступны ему с разных устройств. Гостевые объявления текущего браузера привязываются при открытии кабинета.
- Уведомления об откликах и статусах заказов отображаются в кабинете. Отметка о прочтении отправляется отдельной кнопкой.
- Фотографии и размеры с остатками добавляются на странице товара в админке. Отмена через кабинет или смена статуса через админку автоматически возвращает остатки один раз. Отменённый заказ нельзя снова открыть — создайте новый. Прямые SQL изменения статуса обходят этот сценарий.
- Онлайн эквайринг не настроен. Для подключения нужны выбранный платёжный сервис, реквизиты магазина и публичный HTTPS адрес для webhook.
- Персональные Telegram уведомления не подключены. Уже существующая Telegram поддержка настраивается отдельно через команды проекта.

## Резервные копии и восстановление

Перед копированием остановите приём записей на сайт. Команда сохраняет переносимый снимок данных без сессий и производных разрешений:

```powershell
.\venv\Scripts\python.exe manage.py backup_database
```

Копии появляются в `backups/` и содержат личные данные и хеши паролей. Храните их с ограниченным доступом вне веб каталога и регулярно переносите на отдельный носитель. Ежедневный запуск можно назначить в Планировщике заданий Windows с рабочей папкой проекта. Для работающего production используйте согласованный снимок MySQL через `mysqldump --single-transaction` и отдельное резервное хранилище.

Восстановление выполняйте сначала в отдельную пустую базу с теми же миграциями:

```powershell
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py loaddata backups\vetmo-YYYYMMDD-HHMMSS.json.gz
.\venv\Scripts\python.exe manage.py check
```

Тест проекта проверяет создание копии и загрузку данных обратно. Для production дополнительно проверяйте восстановление полной копии MySQL.

## Проверки и журналирование

```powershell
.\venv\Scripts\python.exe manage.py test main
.\venv\Scripts\python.exe manage.py makemigrations --check --dry-run
```

GitHub Actions запускает проверки с MySQL при push и pull request после размещения репозитория на GitHub. Ошибки приложения направляются в stderr — настройте их сбор и хранение средствами сервера. В production используйте WSGI сервер за HTTPS reverse proxy вместо runserver.

Мобильные сетки, размеры элементов форм, клавиатурный фокус и отключение анимации при reduced motion настроены в `main/static/css/community.css`. Перед публикацией пройдите основные формы на реальном телефоне и проверьте внешний вид в браузере.

## Новые возможности и демонстрация

```powershell
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py seed_demo
```

Команда доступна при `DEBUG=true`. Она поддерживает профили с расписаниями и достижениями, публикации, прошедшие и будущие события, пати с откликами, разборы матчей, завершённый и текущий турниры, турнир с открытой регистрацией, опросы и историю кабинета. Публичные тексты оформлены как обычные записи гильдии. Привязки наполнения хранятся в `.local/showcase_records.json`. Повторный запуск сохраняет данные; `--refresh` обновляет связанные записи и даты. Товары пользователя команда не создаёт и не заменяет.

Логины и случайные пароли новых демоаккаунтов сохраняются в `.local/demo_accounts.json`. Это обычные пользователи без доступа к админке. Для примера начните с `demo_vetmo_1`: у него есть заказ и объявления. Войдите за `demo_vetmo_4`, чтобы проверить очередь событий и отклики. Выход доступен в кабинете.

- `/matches` — отчёты о матчах и разборы капитана
- `/tournaments` — турниры и регистрация составов из пяти игроков
- `/polls` — голосования и результаты
- `/account/favorites/` — избранные игроки объявления и товары
- `/account/reset/` — восстановление пароля

Сетку турнира и результаты организатор заполняет вручную в админке. Таблица побед считается автоматически по завершённым матчам. Достижения выдаются в админке через `PlayerAchievement`. Статистика OpenDota загружается вручную по ID реального матча на странице разбора пользователем с правом изменения разборов.

Капитан пати занимает свою позицию и принимает ещё четыре отклика на разные позиции. Отклик без позиции можно отправить но нельзя принять до уточнения позиции. Закрытие объявления и отмена записи подтверждаются в браузере.

Отмена регистрации освобождает место первому участнику очереди. Авторизованному игроку отправляется уведомление в кабинет. Гости проверяют свой статус на странице событий из того же браузера.

Настройка открытого профиля находится в кабинете. Скрытый профиль не показывается в списках на главной в избранном и по прямой ссылке.

## Письма и защита форм

По умолчанию письма восстановления выводятся в терминал `runserver` вместо настоящей отправки. Это позволяет открыть ссылку и проверить смену пароля локально. Для доставки писем задайте `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend` и заполните `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `DEFAULT_FROM_EMAIL` в `.env`. Реальная SMTP доставка требует реквизитов почтового сервера.

Почта запрашивается при регистрации и меняется в кабинете с подтверждением текущего пароля. Демопочты используют зарезервированный домен example.com.

Формы создания заявок заказов и объявлений защищены от повторной отправки из одной сессии в течение минуты. Основные публичные формы ограничены десятью запросами в минуту на адрес и обработчик. Счётчики хранятся в таблице `FormThrottle`; заголовок X-Forwarded-For не используется. За reverse proxy настройте доверенный реальный адрес на уровне сервера. CAPTCHA не требуется для локальной демонстрации.

## Планирование игр и разборы

- В кабинете задаются дни недели, начало и конец игры, а также IANA часовой пояс (`Europe/Moscow`, `Asia/Yekaterinburg`). Интервалы через полночь поддерживаются. Текстовое расписание остаётся комментарием. Совпадение расписаний показывается при пересечении от 30 минут на ближайшей неделе; неполные расписания не угадываются.
- На странице пати есть пять слотов. Собрав четыре принятых отклика на разные позиции, капитан назначает игру. Участники подтверждают участие и скачивают `.ics`. Смена состава сбрасывает назначенное время и подтверждения.
- `/matches/<id>/` — отдельный разбор с героями, ключевым моментом, удачными решениями и планом следующей игры. Эти поля заполняются редактором в админке.
- Импорт из терминала: `manage.py import_match <ID_разбора> <ID_матча_Dota>`. Нужен доступ к `api.opendota.com`. Сохраняется выбранная статистика без Steam ID игроков. Авторские текст, состав, дата и результат команды не заменяются. При недоступности API ранее сохранённая статистика остаётся на сайте.
- После `backup_database` рядом с копией создаётся `.sha256`. Команда `manage.py verify_backup backups\имя.json.gz` проверяет чтение, структуру и контрольную сумму, не изменяя базу. Это дополняет, но не заменяет пробное восстановление через `loaddata` в отдельную базу.
- Страницы 404/500 используются при `DEBUG=false`; 500 работает без обращения к базе. Мобильное меню доступно с клавиатуры и закрывается по Escape; при отключённом JavaScript ссылки остаются видимыми.
# Обслуживание игровых функций

После обновления примените миграции (`.\venv\Scripts\python.exe manage.py migrate`). Для напоминаний перед игрой и завершения временных статусов нужен периодический запуск `manage.py guild_tick`. На Windows создайте задачу в Планировщике с повторением каждые 5 минут: программа — полный путь к `venv\Scripts\python.exe`, аргументы — `manage.py guild_tick`, рабочая папка — корень проекта. Используйте то же окружение и базу, что у сайта. Проверка вручную: запустить команду дважды; при неизменном времени игры участнику не должно прийти второе напоминание.

`manage.py weekly_draft` готовит публикацию «Итоги недели» для редакторской проверки. Черновик открывается в админке публикаций. Повторный запуск в ту же неделю сохраняет правки редактора.

`manage.py guild_metrics` выводит сводку по пати. `manage.py rehearse_restore <путь-к-копии.json.gz>` служит для пробного восстановления. Замеры одежды указываются отдельно для каждого размера в админке товара; отсутствующее измерение не подменяется средним по каталогу.
